# Multiparadigm report — `interp/Main.java`

> Language: Java 17 → Java 21 · Subdomain: Interpreter with syntactic analysis (AST + polymorphic operations) · Generated by /multiparadigm

## 1. Detection

- Language and version: Java 17 (input).
- Framework / runtime: none; only `java.util`.
- Detected OO signals: class hierarchy (`Expr` abstract + 4 subclasses), subtype polymorphism via the `accept` method, classic Visitor pattern, encapsulated mutable state (`Map<String,Integer> env` in `Evaluator`), `switch` over operation tag.
- Detected FP signals: none explicit; `accept(Visitor)` follows the spirit of a fold but is tied to inheritance.
- Paradigm balance: **0.92** (mono-paradigm OO; see `MODEL.md` §3.3). Candidate for multiparadigm refactoring because the domain (interpreter with multiple interpretations) puts the Expression Problem under tension and favors introducing M1/M3.

## 5. Refactoring proposal

### 5.1 Conceptual diff

- **AST**: OO hierarchy with `accept` → `sealed interface Expr` + records (Java 17 sealed types + records). One single place declares all nodes; pattern matching over `switch` is exhaustively checked by the compiler (Java 21).
- **Operators**: `String op` → `enum Op { ADD, SUB, MUL, DIV }`. Eliminates the `default` in switch.
- **Visitor**: `Visitor<R>` interface with one method per node → `interface ExprAlg<A>` (Object Algebra). Each interpretation is a value of type `ExprAlg<A>`, not a heavy class.
- **Folder**: polymorphic `accept` → free function `Fold.fold(Expr, ExprAlg<A>): A`. Pattern matching over the sealed interface inside `switch`.
- **State**: mutable `Map env` in the visitor → immutable `Map.of(...)`; the evaluator is a function `evalIn(env): ExprAlg<Integer>`.
- **Business rules**: extracted to `final class Rules { isTruthy, safeDiv }`. Reusable and testable in isolation.
- **External openness**: `@FunctionalInterface Show<A>` so third parties can register print interpretations without touching the core (M2 proxied by Java's functional interface).

### 5.2 After code

See [`after.java`](./after.java). Summary:

```java
sealed interface Expr permits NumLit, BinOp, Var, IfExpr {}    // <<algebra>> base (M3)
record NumLit(int value)                          implements Expr {}
record BinOp(Op op, Expr left, Expr right)        implements Expr {}
record Var(String name)                           implements Expr {}
record IfExpr(Expr cond, Expr thenB, Expr elseB)  implements Expr {}

enum Op { ADD, SUB, MUL, DIV }

interface ExprAlg<A> {                                          // <<algebra>> of interpretations (M1)
    A num(int v);
    A bin(Op op, A l, A r);
    A variable(String name);
    A ifExpr(A c, A t, A e);
}

final class Fold {
    public static <A> A fold(Expr e, ExprAlg<A> alg) {
        return switch (e) {
            case NumLit(int v)                   -> alg.num(v);
            case BinOp(Op op, Expr l, Expr r)    -> alg.bin(op, fold(l, alg), fold(r, alg));
            case Var(String name)                -> alg.variable(name);
            case IfExpr(Expr c, Expr t, Expr el) -> alg.ifExpr(fold(c, alg), fold(t, alg), fold(el, alg));
        };
    }
}

@FunctionalInterface
interface Show<A> { String show(A a); }                          // <<typeclass>>-like (M2)
```

### 5.3 Absorbed anticipated changes

1. **New operation** — add an `Optimizer: ExprAlg<Expr>`:
   - **Before (Java 17 baseline)**: new `Optimizer implements Visitor<Expr>` class with one method per node (4 methods). Touches 0 pre-existing classes but creates 1 new file. **LOC modified: 0; LOC added: ~40** (includes Visitor boilerplate).
   - **After (Java 21)**: new `ExprAlg<Expr> OPTIMIZER` as anonymous instance with 4 methods. **LOC modified: 0; LOC added: ~30**. Better due to less boilerplate, even if not as terse as Scala `val Optimizer = ...`.
2. **New datum** — add a `Lambda(String param, Expr body)` node:
   - **Before (Java 17)**: add `Lambda extends Expr` class (~10 LOC) + add `visitLambda` to `Visitor` (1 LOC) + implement `visitLambda` in EVERY existing Visitor (3 visitors × 5-8 LOC = 15-24 LOC). **LOC modified: ~16; LOC added: ~10**. Suffers Expression Problem.
   - **After (Java 21)**: add `record Lambda(String param, Expr body) implements Expr {}` (1 LOC) + add `Lambda` to the `permits` clause (1 LOC) + add `A lambda(String p, A body)` to the `ExprAlg<A>` interface (1 LOC) + the compiler FORCES updating the 3 interpretations and the `Fold.switch` (3 methods × 2-5 LOC + 1 case ~3 LOC). **LOC modified: ~14; LOC added: ~5**. Better: the change is localized and exhaustiveness is enforced by the typechecker.
3. **Type variant** — add `Bool` and logical operations:
   - **Before (Java 17)**: adding `Ty.TBool` requires changing the `String` to an enum (large refactoring); accepting boolean types in `BinOp` requires loosening the check in `TypeChecker`. **LOC modified: ~30** (the `String` of types is scattered).
   - **After (Java 21)**: `enum Ty { INT, BOOL }` already exists; add variants to `Op` and cases in `evalIn` and `TYPECHECK`. **LOC modified: ~18; LOC added: ~10**. The compiler requires updating all `switch` blocks for exhaustiveness.

## 6. Flexibility delta

### 6.1 Per dimension

| Dimension | Before | After | Delta | Justification |
|---|---|---|---|---|
| Extensibility | 0.42 | 0.74 | +0.32 | Averaging the 3 anticipated changes: LOC_modified/LOC_total drops from ~0.55 to ~0.32. Anchor: Eden & Mens 2006, "the cost of change as a function of where the change happens" |
| Modularity | 0.55 | 0.70 | +0.15 | DIT drops from 2 (Expr → NumLit/BinOp/...) to 1 (flat ADT via sealed); LCOM4 disappears (records have no shared mutable fields); Ce/(Ca+Ce) of the visitors module drops from 0.6 to 0.40 by eliminating the visitor↔hierarchy dependency. Anchor: Kallel et al. 2018 |
| Variation points | 0.40 | 0.74 | +0.34 | Before: 3 fixed visitors; adding one requires implementing 4 methods in a new class. After: any `ExprAlg<A>` value is a pluggable variation point; in addition the `@FunctionalInterface Show<A>` allows third parties to extend presentation without touching the core. Wiring: 1 LOC per interpretation (`Fold.fold(e, MyInterp)`). Anchor: Heinzl & Schreibmann 2018; Heithoff 2023 |

### 6.3 Verdict

- [x] The refactoring is justified by flexibility (delta = +58%, well above the 10% threshold).
- [ ] The refactoring is NOT justified.
- [ ] The refactoring degrades flexibility.

**Comment**: the improvement concentrates in extensibility (Expression Problem absorbed by the ADT + Object Algebra combination) and in variation points (interpretations as values). Modularity improves moderately. Trade-off: the reader needs familiarity with sealed types, records, and pattern matching in `switch`, which require Java 21 (records and sealed are GA since Java 17, but switch over patterns is GA since Java 21). According to Castro (2020) [#30] paradigm alone does not guarantee quality — the gain here depends on the team being on Java 21+ and on the domain (multiple interpretations of an AST) genuinely justifying openness. In projects where only ONE interpretation is foreseen, this refactor would be category 7 ("Not applicable") due to over-engineering.
