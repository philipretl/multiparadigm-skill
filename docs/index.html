The abstraction mechanisms

From the intersection of the 68-primary-study corpus and Narbel's (2007) paradigm classification of patterns emerge five detailed-design mechanisms (M1–M5) and one governing architectural principle (M6). Each mechanism addresses a documented limitation of classic design patterns.

M6 · Governing principle Paradigm composition by subdomain

Unlike M1–M5, it is not a detailed-design mechanism but the architectural principle that governs the application of the other five. It addresses the limitation of single-paradigm design methods: forcing the whole problem into a single conceptual language. Following Coplien (2000) and Vranic (2009), the first design decision assigns each subdomain of the problem —data, control, concurrency, presentation— its most natural paradigm; mechanisms M1–M5 operate afterwards, within and across the subdomains thus delimited.

Anchors: Coplien — Multi-Paradigm Design · Vranic — feature modeling · multiparadigm languages such as Oz.

M1 Object algebras / Tagless Final

Limitation it addresses

Factory + Visitor against the Expression Problem: extending data and operations at the same time forces changes to existing code.

Key question

How do I grow types and operations simultaneously without touching existing code? · Mechanism: data are functions awaiting an interpreter (polymorphic algebraic signature).

Proposal

Generalize them into a polymorphic algebraic signature that allows simultaneous extension along both dimensions without touching existing code.

Anchors: Oliveira & Cook 2012 · Oliveira & van der Storm 2015 · Oliveira et al. 2013.

M2 Type classes / Generalized Interfaces

Limitation it addresses

Adapter and Strategy: giving existing types new behavior requires modifying or wrapping them, coupling the design to the hierarchy.

Key question

How do I give new behavior to types that already exist without modifying or wrapping them? · Mechanism: an external party supplies the implementation (type class instance) — open, retroactive ad hoc polymorphism.

Proposal

Attach behavior to types without modifying their definitions: open, retroactive ad hoc polymorphism.

Anchors: Wehr & Thiemann (JavaGI) · Odersky et al. (Simplicitly).

M3 Algebraic data types + Pattern Matching

Limitation it addresses

Visitor: achieving case-based decomposition in OO imposes double dispatch and the accept/visit scaffolding that pollutes the base classes.

Key question

How do I decompose by case without the accept/visit scaffolding of the Visitor? · Mechanism: sealed ADT + exhaustive match — the compiler verifies no case is missing.

Proposal

Closed types with explicit syntactic decomposition, separating data from operations without giving up exhaustiveness checking.

Anchors: Emir et al. (Matching Objects with Patterns) · Löh & Hinze (Open data types).

M4 HOF + Closures + FP Composition

Limitation it addresses

Strategy, Command, and Iterator: representing pure behavior requires erecting class hierarchies whose indirection adds no value.

Key question

How do I represent pure behavior without erecting class hierarchies? · Mechanism: a function as a value — lambda as strategy, closure as command, pipeline as iterator.

Proposal

First-class values: a lambda as a strategy, a closure as a command, a map/filter/reduce pipeline as an iterator.

Anchors: Bringert & Ranta · Sousa & Ferreira · Crichton (Typed Design Patterns).

M5 Reactive signals / Actors / Continuations

Limitation it addresses

Observer: the subject–observer coupling and the manual inversion of control scatter the update flow and make it hard to reason about.

Key question

How do I propagate changes without coupling subjects to observers? · Mechanism: declarative dependency graph — the runtime propagates the change, not the programmer.

Proposal

Declarative change propagation (signals), or actors that unify thread- and event-based concurrency through explicit continuations.

Anchors: Salvaneschi et al. (RP comprehension) · Haller & Odersky (Actors that Unify).

Application guide

Four steps, iterable throughout the design

The guide organizes the application of the technique into four sequential steps that can be iterated during detailed design.

1

Decomposition and classification

Decompose the requirements into candidate components and apply the decision scorecard (Table 4.1) to each one. The wizard on this page automates this step.

Output: components classified as mutable entity (OO) or value/function (FP)
2

Hybrid interface definition

Design the interfaces of the main classes (OO) and, at the variation points that require flexibility, replace single-method interfaces with function-typed parameters. This substitution applies the Open/Closed principle through functional composition (Narbel 2007).

Output: OO contracts with functional variation points
3

Visual modeling

Build the class and sequence diagrams with the lightweight UML profile, explicitly marking <<pure>> methods and <<ValueObject>> classes so the decisions remain visible from the design onward.

Output: diagrams with explicit paradigm decisions
4

Refactoring toward immutability

Review the preliminary design looking to reduce shared mutable state. If an OO class has a majority of <<pure>> methods, consider turning it into a functional module or a <<ValueObject>>; if a procedural sequence can be replaced by function composition, do it.

Output: design with minimal, localized mutable state

Notation

Lightweight UML profile

Extends class and sequence diagrams through stereotypes (<<...>>) and tagged values ({...}) without modifying the UML metamodel: compatible with standard tools. It continues the line of Heinzl & Schreibmann (2018) and addresses the lack of notation for functional design pointed out by Motara (2021).

Evaluation model

How to measure design flexibility

Flexibility is not an absolute property of software: it is relative to a class of changes declared in advance (Eden & Mens, 2006). The technique evaluates the resulting design along three operational dimensions.

Extensibility

Ability to add new types or new operations without altering what already exists.

Evaluated with evolution steps that introduce a domain type or an operation over the existing types (modified vs. added vs. preserved LOC).

Modularity

Decomposition into cohesive, loosely coupled parts.

Evaluated with steps that redefine an architectural boundary or redistribute responsibilities (Ca/Ce coupling, instability, cohesion).

Variation points

Ability to change behavior by parameter or by swapping implementations.

Evaluated with steps that replace an algorithm or introduce a one-off criterion (explicit pluggable variation points, wiring cost).

The core idea: declare the evolution steps before measuring

An «evolution step» formalizes an anticipated change: original problem, modified problem, previous implementation, and adjusted implementation. Measuring flexibility reduces to measuring the cost of transforming the first implementation into the second: how many modules change, weighted by a complexity metric (LOC, cyclomatic complexity, timed effort). Declaring the set of steps up front is essential: it prevents the later choice from biasing the result.

Cost O(|N|) — hard → Cost O(1) — easy

A step is easy if its cost does not grow with the size of the implementation (constant, O(1)) and hard if it grows linearly (O(|N|)) with respect to, for example, the number of domain types or operations. The technique pays off when it moves selected steps from O(|N|) to O(1) without degrading the cost of the rest.

Standard anticipated changes in the case study: (1) a new operation over existing data, (2) a new datum/node over existing operations, (3) a new type variant.

Tooling

The /multiparadigm agent

The technique is operationalized as a portable command (Claude Code/Cowork, GitHub Copilot, Cursor, ChatGPT/Grok) that analyzes code through the multiparadigm lens and proposes refactorings justified with the criteria, mechanisms, and patterns on this page. It issues no «OO is better» or «FP is better» verdicts: it follows Coplien — the domain chooses the paradigm.

The 6 phases of the analysis

Phase 1
DetectionLanguage, OO/FP signal balance, and the code's subdomain (CRUD, AST/interpreter, ETL pipeline, parser…).
Phase 2
Pattern reportCatalog patterns (or ad hoc equivalents) detected, their current form, and known tensions (e.g. Expression Problem).
Phase 3
Implicit business rulesRules entangled with the mechanics of the code, with a suggested paradigm to encapsulate each one.
Phase 4
Applying the techniqueFor each finding: assignment criterion (1–6), mechanism (M1–M6), and refactoring category (1–8).
Phase 5
Refactoring proposalConceptual diff, «after» code with UML stereotypes as comments, and the anticipated changes the new design absorbs.
Phase 6
Flexibility deltaBefore/after per dimension (extensibility, modularity, variation points) plus an aggregate Flex-Score. Honest deltas: if it does not improve, it says so.

Three decision modes (human-in-the-loop)

Autonomous

When a finding unambiguously matches a scorecard criterion —e.g. a pure transformation implemented with accidental mutable state— the agent applies the criterion and records the justification without asking.

Guided

When the evidence is ambiguous or the change affects the module's public contracts, the agent presents the alternatives with their anchoring to the criteria and asks the developer, who decides. The interaction is recorded.

Universal audit

Every modification —autonomous or guided— is delivered as a reviewable proposal (pull-request style) that developers approve, adjust, or reject. No change enters the design without human review.
